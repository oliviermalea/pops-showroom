# Test Rules — ShowRoom

- Every module must have its own test project under `tests/`.
- Endpoint tests and Assembler tests are the highest testing priority and are mandatory for each HTTP feature.
- For create features, endpoint tests must assert `201 Created`, Location header consistency, and a response payload containing only the created `PublicId` string when the contract is identifier-only.
- Use xUnit with AAA structure and name the SUT variable `sut` when relevant.
- Prefer `AwesomeAssertions` for assertions in module tests.
- Add unit tests for domain behavior, configuration, and edge cases.
- Add integration tests for endpoints and persistence when the module exposes HTTP features.
- Keep test fixtures aligned with the module being tested, following the established module test pattern.
- Integration isolation uses the shared **`ShowRoom.Testing`** project (referenced by every module test project): `BusinessWebFactory : WebApplicationFactory<Program>` (owns a Testcontainers PostgreSQL container + virtual `ConfigureModuleTestServices`/`InitializeModuleTestServices` hooks), `Database/DatabaseContainer` (xUnit fixture), `Database/IDatabaseConfiguration`, `Configuration/ConfigurationExtensions` (`WithContainerDatabaseConfigured`, `SetFakeSystemClock`), `Http/HttpResponseMessageExtensions` (`GetIdFromLocationHeader`), `BusinessBaseIntegrationTest<TFactory>`.
- For each module exposing HTTP endpoints, include a dedicated `<Module>BusinessWebFactory : BusinessWebFactory` that, in `ConfigureModuleTestServices`, removes the app's `DbContextOptions<<Module>Context>` and re-adds `AddDbContext` pointed at the factory container, and migrates in `InitializeModuleTestServices`. This requires the module to register its DbContext via plain `AddDbContext` (`DatabaseModule.AddDatabase`), NOT Aspire's `AddNpgsqlDbContext` (whose options action cannot be cleanly removed).
  - **Exception — modules using the transactional outbox (§3.3.2):** the factory must **NOT** repoint the DbContext, and does not use the separate `DatabaseContainer` / `WithContainerDatabaseConfigured` / `<Module>DatabaseConfiguration` path. Because the module DbContext and the Wolverine message store must share ONE database (the outbox writes envelopes through the context's own connection), the factory binds `ConnectionStrings:showroom` to its OWN `_postgreSqlContainer` through `HostConfigurationOverrides` — visible at build time to both `AddDatabase` and `ConfigureShowRoomMessaging`, pointing both at that single, isolated, per-test-class throwaway container. It migrates in `InitializeModuleTestServices`, and clears Wolverine storage in `DisposeAsync` (`ClearAllWolverineStorageAsync`, capturing the `IHost` via a `CreateHost` override). External transports are stubbed by the base factory (`DisableAllExternalWolverineTransports`), so no broker is needed. Endpoint tests take only `IClassFixture<<Module>BusinessWebFactory>` and enable `Messaging:UseTransactionalOutbox` in `appsettings.IntegrationTests.json`.
- For each module exposing HTTP endpoints, include a dedicated `<Module>DatabaseConfiguration : IDatabaseConfiguration` that externalises the connection string under the key the module's `AddDatabase` reads. (Outbox modules are excepted — see the exception above; they self-configure the container via `HostConfigurationOverrides` and have no `<Module>DatabaseConfiguration`.)
- Endpoint tests are `IClassFixture<<Module>BusinessWebFactory>` + `IClassFixture<DatabaseContainer>` and MUST go through `factory.WithContainerDatabaseConfigured(...)` — never the bare base factory (the app's `AddDatabase` throws without a connection string). Seed via that configured factory's DbContext (or via HTTP). (Outbox modules are the documented exception above — they self-configure via `HostConfigurationOverrides`.)
- **Transactional-outbox proof (§3.3.2), broker-free:** a module that publishes IntegrationEvents through the outbox includes a dedicated test that asserts the event is emitted, WITHOUT a real broker: with external transports stubbed, run the trigger inside `factory.Services.TrackActivity().Timeout(...).ExecuteAndWaitAsync((Func<IMessageContext,Task>)(async _ => { /* HTTP POST */ }))` and assert `tracked.Sent.SingleMessage<TEvent>()`.
- **Consumer retry/dead-letter proof (§3.3.3), real broker:** a module that CONSUMES an IntegrationEvent includes ONE dedicated end-to-end test backed by **PostgreSQL + RabbitMQ Testcontainers** (`StubExternalTransports => false`, both connection strings + `Messaging:UsePersistentMessageStore`/`MessageStoreSchema` via `HostConfigurationOverrides`, `ClearAllWolverineStorageAsync` on teardown, and a test-only `IWolverineExtension` publish route to inject the message). It asserts a well-formed message is handled (`tracked.MessageSucceeded.SingleMessage<TEvent>()`) and a poison message is dead-lettered (`tracked.MovedToErrorQueue.SingleMessage<TEvent>()`), driving both with `TrackActivity().WaitForMessageToBeReceivedAt<TEvent>(factory.Host).ExecuteAndWaitAsync(c => c.PublishAsync(evt))`.
